  [HIGH] apps/api/src/modules/calendar/public-booking.router.ts:464-465 — non-atomic-booking-caps
    Issue    : Concurrent anonymous requests can bypass the booking abuse caps because checking and recording an attempt are separate operations.
    Evidence : `await assertBookingCaps(ctx.prisma, keys, now)` precedes `await recordBookingAttempt(ctx.prisma, keys)` outside the advisory-locked transaction. With two existing email attempts, multiple concurrent requests can all observe a count of two and insert another attempt, exceeding the three-per-day cap; the later booking lock does not recheck these caps.
    Fix      : Serialize the cap check and attempt insertion per tenant in a dedicated transaction using a shared advisory lock, and commit that attempt before processing the booking so failed bookings remain counted.
