  [MEDIUM] apps/api/src/modules/calendar/booking-email.ts:108-119 — unverified-recipient-content-injection
    Issue    : The booker confirmation goes to an unverified address that anyone can type in, and it repeats the free-text booker name in the body. An anonymous visitor can therefore make the firm's own email domain deliver attacker-written text to any inbox.
    Evidence : textBody: [`Hello ${d.bookerName},`, ...] and htmlBody: `Hello ${escapeHtml(d.bookerName)},`. The module header says the booker mail "never echoes free-text answers" because the address is unverified, but `name` is also free text. publicBookInputSchema only strips control characters and allows up to 200 characters, so a name like 'Your account is locked, reset it at evil.example' is accepted. Escaping stops HTML injection but not phishing text, and the text body puts it in raw. The only limit is 3 per email per tenant per 24 h and 10 per IP per hour, so rotating IPs or target addresses (each new address has its own 3/day allowance) turns the endpoint into a spam/phishing relay signed by the firm. The tests only check that the name is HTML-escaped, so they share the same assumption.
    Fix      : Leave the booker-supplied name out of the booker confirmation (for example a fixed 'Hello,'), or shorten it hard to a plain-name pattern (letters, spaces, hyphens, apostrophes, about 60 characters) before it goes into any email sent to the unverified address.
