  [MEDIUM] apps/api/src/modules/legal/appointments.router.ts:497 — incomplete-concurrency-guard
    Issue    : Staff-created appointments never take the per-tenant `booking:<tenantId>` advisory lock that public bookings rely on, so a public booking and an in-app appointment can both take the host's same slot, or both get past the firm's daily cap.
    Evidence : public-booking.router.ts serialises bookings with `lockTenant(tx, tenantId, 'booking')`, then re-reads host busy time and the tenant-wide daily count inside that lock. Its header claims 'two bookings of one slot (or the last slot under the daily cap) cannot both win'. event-types.router.ts takes the same lock for config writes. The internal `appointments.create` path (this PR adds `assertEventTypeInTenant` at line 497 and `linkEventType` afterwards) runs `assertAppointmentWithinAvailability` and conflict detection through ScheduleAppointmentUseCase. It takes no lock at all (grep finds no `pg_advisory` or `booking:` in appointments.router.ts). Here is the race: a staff member creates an appointment for the host at 10:00 while a visitor books 10:00. The public transaction reads busy time before the staff row commits, and the staff conflict check reads before the public row commits. Both commit. The daily-cap count races the same way. The unit tests only check lock ordering among public bookings and event-type writes, so they can't catch this.
    Fix      : Take the same lock in the internal create path before its availability, daily-cap and conflict checks. That means `SELECT pg_advisory_xact_lock(hashtextextended('booking:' || tenantId, 0))` inside the transaction that writes the appointment, so ScheduleAppointmentUseCase needs to run on a caller-supplied transaction. Or narrow the router comment and ADR-083 to say the guarantee only holds between public bookings.
