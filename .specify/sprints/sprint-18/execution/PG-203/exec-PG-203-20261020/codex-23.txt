UNWAIVED FINDINGS (BLOCKING):
  [MEDIUM] apps/api/src/modules/calendar/booking-abuse.ts:74-80 — abuse-cap-enables-booking-lockout
    Issue    : The per-event-type cap (30 per hour) counts every anonymous attempt, failed ones included, across the whole tenant. Anyone can therefore use it up and block all real visitors from booking that event type, again every hour.
    Evidence : `prisma.bookingAttempt.count({ where: { tenantId, eventTypeId, createdAt: { gt: lastHour } } })` is compared to `BOOKING_CAPS.perEventTypePerHour`. In public-booking.router.ts (lines 532-536) the attempt is recorded in its own committed transaction before the slot is checked (`recordBookingAttempt` runs ahead of the booking transaction, and the comment says 'committed before the booking so a failed booking still counts'). An attempt for a slot that does not exist, or one already taken, still adds a row. The email cap (3 per 24 h) and IP cap (10 per hour) are the only per-sender limits, so 3 IPs × 10 throwaway emails = 30 junk requests per hour are enough. After that, every real booker gets the same generic TOO_MANY_REQUESTS ('Too many booking attempts. Please try again later.') and the firm never sees the bookings it lost. The unit test asserts that the 30th attempt throws, which is the same assumption, so the lockout is not caught.
    Fix      : Stop letting the shared per-event-type cap be used up by attempts that never booked. Option 1: count only attempts that reached or passed the slot check. Option 2: count successful public bookings (appointments with bookedVia='PUBLIC_LINK') per event type per hour. Option 3: keep the attempts count but record the attempt only after the honeypot, required-answer and slot-validity checks pass. Keep the per-email and per-IP caps on all attempts.
